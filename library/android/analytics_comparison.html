Wiom TV · Analytics Strategy

How we measure the app — ours vs production, and the gold standard

A code-level comparison of the analytics in our zero-based app (com.wiom.tv.zb, v1.3-pilot) and Ashutosh's live production app (com.wiomtv.android.prod, v11.0.2), then a recommended target architecture. Direct answer to: "should we rely on CleverTap alone for everything?"

2026-06-30 · grounded in both codebases + the existing production deep-dive

The one-line verdict

CleverTap is the right engagement layer — but "CleverTap for everything" is the wrong frame for a streaming app running on Wiom's own ISP.

CleverTap is elite at who watches, how often, and how to message them. It is the wrong tool for does the video play smoothly at fleet scale (QoE), did it crash (stability), and can I join watch-behaviour to our router/household graph in Snowflake (ownership). The gold standard keeps CleverTap for engagement and adds three thin, purpose-built layers behind the single Telemetry façade we already have.

What production does better

  • QoE event schema — error_bucket / error_stage / error_code taxonomy, and the recovery_actioned → recovery_resulted pair (with time_to_recover_ms).
  • Network-context session — is_on_wiom_net, SSID, RSSI, link-speed, ethernet, partner_id. This is gold for a Wiom-ISP app and we don't capture it.
  • CRM profile — rich per-household properties enabling segmentation/messaging.

What we do better

  • One façade, many sinks — instrument once, route anywhere. Theirs is welded to CleverTap.
  • Privacy-correct — hashed phone, no committed secrets, no force-crash in the build.
  • No dead events — newer SDK, durable offline queue (just added), honest taxonomy.

2 · Why CleverTap-only is not enough

CleverTap-only forces one tool to do four jobs. It is genuinely excellent at one of them.

QoE doesn't fit the event model

Streaming health is rates & percentiles — rebuffer ratio, video-start-failure %, p95 TTFF, exit-before-video-start. CleverTap is an event/funnel CRM; pushing per-segment telemetry into it explodes event volume & cost and still gives you no Conviva/Mux-style QoE dashboard. Production already strains this — it pushes raw rebuffered/play_error events into a CRM.

It can't do crashes/ANRs

Both apps still need Crashlytics — proof that "CleverTap for everything" is already false in practice. ANRs and non-fatals need a stability backend, not a CRM.

You don't own the data

Raw events live in CleverTap's platform. Arbitrary SQL, long-horizon retention, and joins to the rest of Wiom's data are limited and export-gated. If we ever drop the vendor, the history is hard to take with us.

…but engagement is its home turf

Active users, retention cohorts, RFM, segments, and — crucially — push / in-app campaigns back to the TV. Keep CleverTap for exactly this. Don't rip it out; scope it.

3 · The gold standard — one façade, four purpose-built layers

We already have the hard part: a single Telemetry seam. The gold standard is to make that seam a typed event router that fans out to the right backend per event class — instead of dumping everything into one CRM.

app code → one typed Telemetry façade (durable offline queue, consistent household-id, PII hashed)
↓   routes by event class   ↓
CleverTap · QoE pipe · Crashlytics · Wiom warehouse (Snowflake)
1

Engagement → CleverTap (keep — already have it)

Only the events that drive segmentation & messaging: app_open, channel_view(duration+genre), login funnel, favourites, DAU/WAU, retention. This is what unlocks push/in-app campaigns back to the household later. Stop sending it the QoE firehose.

2

QoE / streaming → dedicated path (build now on our own events; buy Mux/Conviva later if scale demands)

Video-start-time, video-start-failures, rebuffer ratio, error taxonomy, per-channel health. Adopt production's schema — error_bucket/error_stage/error_code + the recovery_actioned/resulted pair. We already compute TTFF/stall in QoeLog; aggregate client-side (per-session, not per-segment) and land it in the warehouse. Dashboards live in Metabase — the tool you already use. This layer is how we prove the smoothness work at fleet scale.

3

Stability → Crashlytics (keep + finish wiring)

Crashes already auto-capture. Add what production only stubbed: an ANR watchdog and non-fatal logging for stream_dead / decoder failures with channel context. Set the Crashlytics user-id to the same household-id used everywhere else.

4

Ownership → our own warehouse firehose → Snowflake (the differentiator — neither app has it)

A durable, batched, append-only event stream to a cheap collector (HTTP → object store → Snowflake). Gives full data ownership, unlimited retention, arbitrary SQL, no per-event vendor cost — and one capability no third-party SDK can give us:

★ The Wiom superpower: the TV runs on Wiom's own router. Land watch-behaviour next to DAILY_DATA_USAGE_DT (ROUTER_MAC ↔ MOBILE) and you can join what a household watches → which router → which partner → billing. That graph is impossible through CleverTap/Mux and is the single strongest reason not to be CleverTap-only.

Non-negotiable design principles (carry from our app, fix from theirs)

  • Instrument once — typed event taxonomy (sealed classes) behind the façade; the router decides the sink.
  • Durable offline queue — cheap TVs + flaky AirFiber drop events; Room/WorkManager-backed retry + batching.
  • One identity everywhere — same hashed household-id in CleverTap, QoE, Crashlytics, warehouse, so all four join.
  • Sample the firehose — aggregate high-frequency QoE per-session client-side; never per-segment to a CRM.
  • PII hashed, secrets out of VCS — keep our discipline; never repeat production's plaintext phone / committed keys.
  • No aspirational dead events — an event exists only if something fires it.

4 · What this means for our app (phased)

PhaseDoWhy now
Now
(pilot)		 Keep CleverTap (engagement) + Crashlytics. Upgrade QoE events to production's schema (error_bucket/stage, recovery pair). Add a session_started event with the Wiom network context (is_on_wiom_net, ssid, rssi). Wire ANR + non-fatals. Cheap, all behind the existing façade, and it closes our only real gaps vs production — without inheriting their mess.
Next
(scale prep)		 Stand up the warehouse firehose (own collector → Snowflake) and dual-write engagement + QoE to it via the façade router. Build QoE + watch dashboards in Metabase. Ownership + the router/household join. This is the layer that makes the data usable by you, in the tools you already live in.
Later
(if needed)		 Only if QoE scale/turnkey dashboards justify it: add Mux Data / Conviva for streaming analytics. Otherwise keep QoE on Snowflake+Metabase. Buy vs build decision deferred until volume proves it — no premature vendor cost.
