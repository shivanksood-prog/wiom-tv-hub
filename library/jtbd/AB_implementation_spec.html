First-Session Engagement A/B/C Experiment

Three arms, each on one-third of enrolled new users, to lift first-session engagement — first through activation, then through retention to better channels.

Objective
Lift first-session engagement — via activation, then retention to better channels. North Star = engagement/user; activation = fast gate.
Success
An arm beats C on activation ≥~20% rel. (≥2 wks, ≥150/arm), confirmed by avg watch/user, no bounce/latency regression.

Hypothesis: a new user dropped onto channel 1 in channel-number order wastes time finding something good. Orienting them (A) or surfacing genuinely-engaging channels first (B) gets them to watchable content faster → higher activation, longer watch, better return. Live readout: /tv/experiment1.

1 Experiment design

Arms & split

  • 3 arms — C, A, B — even split, 33.3% each of enrolled new users.
  • Assignment is deterministic & sticky: hash(uid) % 3. Same device → same arm forever.
  • New users only. Existing users keep today's experience (variant = null) and are excluded from the read.
// public/wiom-tv.html — sticky assignment + new-user enrollment
const ARMS = ['C','A','B'];
function _hash(s){ let h=0; for (let i=0;i<s.length;i++) h=(h*31+s.charCodeAt(i))|0; return Math.abs(h); }
let enrolled = _uidNew ? (localStorage.setItem('wiom-tv-enrolled','1'), true)
                       : localStorage.getItem('wiom-tv-enrolled')==='1';
const variant = (EXPERIMENT_ON && enrolled) ? ARMS[_hash(uid) % 3] : null;
Verified locally: over 30k synthetic uids the split was 33.3 / 33.0 / 33.7%.

Validity hygiene

  • SRM check (built into the readout): enrolled counts must be ~33/33/33, else bucketing is broken.
  • Sticky assignment so retention isn't contaminated. A/A sanity: C is a real arm.

4 Ordering algorithm (Arm B) — engagement stick-rate

Popularity is a stick-rate, not raw watch-time — so it can't be gamed by position or inflated by idle/left-on streams.

// within each genre, over a rolling 14d window
rate(ch) = (distinct people who watched > X sec) / (distinct people who tuned)
pop(ch)  = rate(ch)            if tunes(ch) ≥ TUNE_MIN
         = genre MEDIAN rate   otherwise → thin/new channels keep getting shown & tested
score    = pop(ch) + K · MINEnorm(ch)     // MINE = this device's own engaged tunes (0 at cold-start)
  • Removes the biases of raw watch-min: dividing by who-tuned → no position bias · the >X sec bar + distinct people → no idle/binge inflation · tune gate + median → no thin-data noise & new channels stay in rotation.
  • Errors bake in by design — a failed/partial tune counts in the denominator but never reaches X sec, so error-prone channels sink.
  • Denominator = distinct tuners (not raw tune count) so a loyal niche channel isn't deflated by re-tunes; tune count is the confidence gate.
  • Evolves live — recomputed each /api/order call, adapts with every tune. Hero per genre (Arm A landing) = top stick-rate.

X engagement bar30sAbove the <5s "zap" floor, below the 60s activation bar — dense, stable "actually watched" signal (→ 60s to align with the activation OEC)

Applied slot-preserving on the client: each genre keeps its existing positions; only the channels inside those slots are resequenced — so genres don't move, and there's still zero UI change.

8 Scaffolding for iterative experiments

Secondary objective: the A/B/C harness is built to host a sequence of experiments on the same enrolled cohort with near-zero new plumbing.

  • Salted assignment — hash(uid + '|' + EXPERIMENT_ID) % 3. Bump EXPERIMENT_ID (fse_v1 → fse_v2) → the cohort re-randomizes cleanly, so a user isn't stuck in the same arm across experiments.
  • exp on every event + an experiment column → the readout filters by experiment (/api/experiment?exp=fse_v2); each experiment's data is cleanly separable in one table.
  • Reusable readout — /tv/experiment + the headline metrics are experiment-agnostic.
To launch experiment N+1: (1) bump EXPERIMENT_ID; (2) define what the arms do (the only new code); (3) read /tv/experiment?exp=<id>. Bucketing, enrollment, the event pipeline, cohort tracking and dashboard already exist.
Caveat: sequential experiments on the same users carry learning/carry-over risk — re-randomization fixes assignment balance, not history. For exposure-sensitive effects, use a fresh-user window or hold-out.
