Unmute funnel: the overlay works — reaching it is the problem

Live analytics.db · window 3 Jul 05:40 → 8 Jul 07:57 UTC (clean unmute-instrumentation era) · sessions with session_start · generated 8 Jul 2026
64% of sessions that see the "tap to unmute" overlay go on to unmute. But 44% of launches never see it at all — they bounce before playback settles.

Unmute conversion is not gated by the overlay UX: once shown, it converts well (55.9% tap it directly, and more unmute via the mute button or keyboard). The leak is upstream — 72% of launches die in under 60 seconds, and in those sessions only 52% ever reach the prompt and only 27% unmute. Sessions that survive 1–5 min unmute at 59%. Fixing time-to-stable-playback moves this funnel more than any overlay tweak.

The two big non-engaged masses are different problems. A2 (26.1% — playback never started) is a TTFF / cold-start problem. B3 (18.9% — got picture and the nudge, left silent in ~6s) is a first-content / first-impression problem. Together they are 45% of all launches — the sub-60s bounce in two shapes with two distinct fixes.
Caveats. (1) B5 conceals a real ninth bucket — B5a, "browser never restricted autoplay": sound on from frame one, nothing was ever muted, so the session emits no prompt / mute / unmute event at all and is indistinguishable from true silent viewing (B5b) in today's data. Evidence B5a exists and is sizeable: 115 of 340 B5 sessions (34%) belong to uids that had unmuted in an earlier session — exactly the engagement history Chrome's Media Engagement Index rewards with unrestricted autoplay; B5's profile (median 36s, 40% ≥60s, 42% interaction) resembles sound-on viewing, not B3's 6s silent bounce; and 3 B5 sessions prove sound-on via later mute/volume events. Bounds: B5a is between ~1% (proven floor) and 12.9% (all of B5) of launches, plausibly ~4%+ — and the true "watches but won't unmute" audience is correspondingly 5.5–18.4%. Only the autoplay_sound_ok beacon in the play()-resolve path resolves this. (2) The A2/A3 boundary inherits the same gap — the prompt fires on manifest-parse, before first frame, so a few "no-frame" sessions legitimately carry prompts. (3) Buckets are event-inferred from a live DB; counts drift a few sessions per re-query.

P1 · Instant-on TV (A1+A2 — 28.4% of launches)

Why this is the job: a TV that shows nothing for 5s is a broken TV; these users left at median 3s. No unmute, guide, or content work matters until picture exists — this JTBD gates every other one.

Solution: (a) poster frame at first paint — a static image of the boot channel rendered before any JS/HLS work, swapped out on loadeddata (the hook already exists as reportOk); (b) boot on the lowest-TTFF healthy channel — we already collect ttff_ms and playback_error per channel, so the boot slot can be earned, not fixed (compatible with arm B's boot-first design); (c) hls.js startLevel=0 — start at the lowest bitrate and adapt up; on 2–4GB phones on 2G/3G this converts "nothing" into "something" seconds earlier.

No-new-problems check: all engineering-side, zero user effort. One trap: a poster that lingers reads as a frozen TV — the swap on first real frame is mandatory, and the existing CRT static should keep running under it as the "warming up" cue. Lowest-bitrate-first briefly costs sharpness; on this audience's devices that trade is free.

P2 · Silence must be legible (B3 — the 179 persuadable lingerers)

Why this is the job: a silent TV screen has two readings — "muted, tap here" or "broken". Users who leave at median 6s chose the second. The prompt's job is to force the first reading in under a second, and today it argues in the wrong language: the copy is literally "Tap to unmute", in English, to a Hindi-first audience (the PMF survey already ships in Hindi for the same reason).

Solution: (a) Hindi-first copy — "आवाज़ के लिए कहीं भी टैप करें" with a pulsing speaker icon; (b) gesture-unmute (coded, pending review) makes "कहीं भी / anywhere" literally true — the promise and the mechanics match; (c) muted-watchable boot channel — prefer channels that communicate value with sound off (news with tickers) for the boot slot, so the silent first seconds still show a working, information-rich TV rather than a mute talking head; (d) stop yanking the overlay — see P3; a fifth of these users had the prompt removed by the app itself within 5s.

No-new-problems check: zero added steps — the overlay is already a full-screen tap target, we only change what it says and how long it honestly stays. Copy is a no-risk change. Muted-watchable boot ordering also serves P4's quiet viewers and costs sound-on users nothing.

P3 · A second chance at sound (B5b — plus the 21% yanked-prompt sessions)

Why this is the job: today the unmute moment is one-shot: loadStream() hides the overlay on every channel load — including dead-channel auto-skips where the user did nothing (80 sessions) — and once suppressed it never returns, because muted play() resolves and never re-triggers the prompt. The user isn't refusing sound; the app stopped offering it.

Solution (layered, least→most visible): (a) gesture-unmute — coded, pending review/deploy: forcedMute flag marks browser-forced mutes; first pointerdown/keydown anywhere unmutes only those; (b) don't hide the overlay on loads while forcedMute — especially auto-skips — and re-show it on the next tune if still force-muted; (c) persistent corner badge (crossed speaker, subtle pulse) whenever force-muted: the always-available, never-blocking affordance.

No-new-problems check (thought through): Startle risk — sudden audio on a tap can blast; ramp volume 0→100% over ~400ms and show a 1.5s toast "आवाज़ चालू ✓" with the mute button adjacent, so an unwanted unmute is reversible in one tap. Scroll vs tap — pointerdown fires on scroll-intent in the guide, so a browsing user could get audio mid-scroll; if review deems this a real risk, trigger on pointerup with <10px movement (a true tap) instead. Deliberate silence protected — mute button and M-key clear forcedMute (verified in the diff), so neither the badge nor any re-shown overlay ever nags a chosen mute. Beacon integrity — verified in the rebased diff (on e803172 / origin‑main): logMute('button') / ('key') / ('overlay') all preserved; the gesture path calls logMute('gesture') before flipping, so unmute lands with a NEW distinct trigger='gesture' — directly measurable as its own path in this report's trigger breakdown; the overlay is excluded from the gesture handler, so 'overlay' attribution is unchanged; all manual toggle sites clear forcedMute.

P4 · Respect my silence (B2)  +  P5 · Don't make me ask twice (B4+B5a)

P4 — the solution is restraint: an explicit mute (button or M-key) is a contract — no re-arm, no badge pulse, no overlay for the rest of the session. This is a gate on P2/P3, not a feature; its cost is zero and its violation would convert 5.5% of satisfied quiet viewers into annoyed ones. Optional serve-the-job: a captions button where the stream carries text tracks (most Indian FTA HLS don't — offer only when present, never promise).

P5 — protect what already works: B4/B5a users get frictionless sound because the browser's Media Engagement Index learned to trust wiom.tv. Our job is to not break that (no domain moves, no iframe embedding — both reset MEI) and to finally see it: the autoplay_sound_ok one-line beacon. Plus volume memory across sessions — the returning user's TV should sound like they left it.
